- 마감까지: 18일

## 1. 방향 판단 — 맞다, 단 조건이 있다

에이전트 + 스킬 구조로 가는 것이 맞다.

- 대회 과제가 **"AI Agent 서비스 개발"**이다. 지금 우리는 기능 하나짜리 도구다.
- 직전 JB Fin:AI Challenge도 전부 에이전트였고 대상작 FinProof도 에이전트였다.
- 스킬 구조는 기획서 ⑥(확장 가능성)을 구조 자체로 답한다.

### 다만 이 조건을 어기면 진다

> **모든 K-스킬은 "설명"이 아니라 "판정"이어야 한다.**

스킬 10개짜리 다국어 챗봇이 되는 순간 우리 차별화가 증발하고 신한 SOL Global(16개어)·광주은행(38개어)과 같은 물건이 된다. `02_차별화.md`에서 확인한 대로 그 자리는 이미 포화다.

모든 스킬은 같은 형태를 가진다.

```
입력  →  법정·계약 기준과 대조  →  판정 + 금액 + 근거 조문 + 다음 행동
```

"알려준다"가 아니라 "당신 경우엔 이게 틀렸고, 얼마고, 근거는 이 조문이고, 여기로 가면 된다"여야 한다.

## 4. ★ S2 출국 정산 — 두 번째로 만들 스킬

S1 다음은 이것이다. 이유가 셋이다.

**금액이 압도적이다.** 출국 시 받을 수 있는 돈이 두 갈래인데 둘 다 큰데다 **따로 청구해야 한다.**

| 항목 | 규모 (월 215만원 × 3년 가정) |
|---|---|
| 출국만기보험 (퇴직금) | 월 임금의 8.3% × 근속 → 약 780만원 |
| 국민연금 반환일시금 | 본인 4.75% + 사용자 4.75% + 이자 → 약 730만원 |
| 퇴직금 − 보험금 **차액** | 사업주에게 별도 청구 (아는 사람 거의 없음) |

> 위 수치는 상수 기반 단순 산출이며 실제는 근속·보수월액에 따라 다르다. 기획서에 넣기 전 재계산한다.

**데드라인이 칼같다.** 출국 1개월 전 고용센터 신고 → **7일 전 보험사 청구** → 미청구 시 3년 시효 → 산인공 휴면보험금. 출국 후에는 해외에서 서류를 넣어야 해서 난이도가 급상승한다.

**판정이 결정론적이다.** 특히 국민연금 반환일시금은 **국적별 상호주의**로 갈린다. 이건 국가 명단이 곧 데이터이므로 코드가 판정한다. (캄보디아는 2023-03-29부터 당연적용으로 바뀌었다 — 오래된 명단을 쓰면 틀린다.)

**입력**: 국적 · 체류자격 · 입사일 · 출국예정일 · 월 임금
**출력**: 받을 금액 추정 + **D-day 타임라인** + 국민연금 수급 가능 여부 + 차액 청구 안내

## 5. S3 근로계약서 — S1의 짝

S1이 사후라면 S3는 사전이다. 같은 기준, 같은 코드, 시점만 다르다.

계약서 단계에서 잡을 수 있는 것: 최저임금 미달 조항, 숙식비 금액(나중에 S1이 대조할 기준값이 된다), 근로시간, 그리고 **위약금·손해배상 예정 조항** — 근로기준법 제20조가 금지한다.

S1과 규칙 대부분을 공유하므로 **추가 비용이 가장 싼 스킬**이다.

## 6. 에이전트의 진짜 일 — 라우팅

사용자는 스킬 이름을 알 리 없다. "S2를 실행해줘"라고 말하지 않는다. 하는 말은 이렇다.

| 사용자가 하는 말 | 라우팅 |
|---|---|
| "월급이 이상해요" / 사진 한 장 | **S1** |
| "다음 달에 고향에 돌아가요" | **S2 — 즉시 D-day 계산** |
| "이 회사에서 일할까 하는데" | **S3** |
| "은행에서 안 된대요" | S4 |
| "세금을 너무 많이 냈어요" | S5 |

**여기가 에이전트여야 하는 이유다.** "다음 달에 돌아간다"는 말에서 *지금 7일 전 청구 기한이 걸려 있다*를 끌어내는 것 — 그건 메뉴로는 안 된다. 사용자는 자기가 무엇을 놓치고 있는지 모르기 때문이다.

에이전트가 판정하지 않는다. **어떤 판정기를 부를지만 정한다.** 판정은 여전히 코드가 한다.

## 7. 기술 구조 — 인터페이스는 이미 만들어져 있다

`service/lib/rules.ts`가 이미 정의한 타입이 그대로 스킬 인터페이스다.

```ts
type Skill = {
  id: string
  트리거: string[]            // 에이전트 라우팅 근거
  run(input): Finding[]       // ← 이미 존재하는 타입
}
```

`judge(payslip) → Finding[]`가 스킬 1호다. 나머지 스킬도 같은 `Finding[]`을 뱉으면 **결과 화면·다국어 설명·금액 집계·검증 콘솔이 전부 재사용된다.** 스킬을 늘려도 UI는 늘지 않는다.

```
사용자 발화 ─→ 에이전트(라우팅, LLM) ─→ 스킬 선택
                                          ↓
                          입력 수집(부족하면 되묻기)
                                          ↓
                          skill.run() → Finding[]   ← 코드, 결정론적
                                          ↓
                          narrate(Finding[], 언어)   ← LLM
```

3단 분리 원칙은 그대로다. 에이전트는 **1단 앞에 붙는 라우팅 계층**이지 판정 계층이 아니다.

## 8. 18일 현실 — 무엇을 실제로 만들 것인가

배포도 안 됐고 1·3단도 미착수인 상태다. 스킬을 10개 벌이면 전부 얕아져서 진다.

| 우선 | 항목 | 근거 |
|---|---|---|
| 1 | 배포 URL | 없으면 결격 |
| 2 | 요율 검증 6건 | 상수가 틀리면 전부 틀림 |
| 3 | **S1 완성** (1·3단 연결) | 이미 판정 엔진 있음 |
| 4 | **S2 출국 정산** | 금액·데드라인이 가장 강함 |
| 5 | 에이전트 라우팅 (S1 ↔ S2 2개만) | 스킬 2개로도 라우팅은 성립한다 |
| 6 | S3 근로계약서 | 여유 있으면 |

**스킬 2개짜리 에이전트도 에이전트다.** 그리고 스킬 2개를 깊게 하는 편이 5개를 얕게 하는 것보다 심사에서 낫다 — 대상작 FinProof도 기능은 하나였다.

S4~S6은 기획서 ⑥ 확장 로드맵에 넣는다. **기능명세서에는 실제 구현된 것만 적는다.**

## 9. 이 문서가 잠근 것

- 에이전트 + 스킬 구조로 간다
- **모든 스킬은 판정이다.** 설명만 하는 스킬은 만들지 않는다
- 에이전트는 라우팅만 한다. 판정은 코드
- 스킬 인터페이스 = `Finding[]` (기존 타입 재사용)
- 예선 범위: S1 + S2, 라우팅 포함
